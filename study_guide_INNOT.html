Label parser
easy
Parse DEVICE_LABELS — a comma-separated string of key=value pairs — into a HashMap<String,String>. Skip empty segments; trim whitespace around keys and values.

Examples

InputOutput
"location=barcelona,type=jetson-orin"{location: barcelona, type: jetson-orin}
""{} (empty)
" key1 = val1 , key2=val2 , "{key1: val1, key2: val2}
💡 Hints
  • Split on ',', then trim() each segment and continue if empty.
  • split_once('=') cleanly separates the first = from the rest.
  • Trim both the key and the value, not just the segment.
✅ Reference solution (Rust) 
pub fn labels(raw: &str) -> HashMap<String, String> {
    let mut map = HashMap::new();
    for pair in raw.split(',') {
        let pair = pair.trim();
        if pair.is_empty() { continue; }
        if let Some((k, v)) = pair.split_once('=') {
            map.insert(k.trim().to_string(), v.trim().to_string());
        }
    }
    map
}
🧪 Tests it must pass
  • test_labels_parsing — two pairs, correct values, len == 2
  • test_labels_empty — empty input ⇒ empty map
  • test_labels_whitespace — " key1 = val1 , key2=val2 , " trims to clean pairs, len == 2

Inference backend resolver
medium
Given an explicit RUNTIME_BACKEND and the LITERT_URL/OLLAMA_URL env vars, resolve which RuntimeBackend to use. Explicit choice wins; otherwise auto-detect with precedence LiteRT > Ollama > Stub.

Rules

RUNTIME_BACKENDResult
"litert"LiteRT (url defaults to http://localhost:8000)
"ollama"Ollama (url defaults to http://localhost:11434)
"stub"Stub — even if URLs are set
emptyauto-detect: LiteRT if its URL set, else Ollama if its URL set, else Stub

The model name falls back to the deployment's model_id unless LITERT_MODEL overrides it.

💡 Hints
  • trim().to_lowercase() the backend string before matching.
  • Auto-detect and the "litert" arm share the "url-or-default + model-or-fallback" shape — factor a non_empty(&str) -> Option<String> helper.
  • Precedence is just the order of your if/else if checks.
✅ Reference solution (Rust) 
pub fn resolve_backend(&self, model_id: &str) -> RuntimeBackend {
    match self.runtime_backend.trim().to_lowercase().as_str() {
        "litert" => RuntimeBackend::LiteRT {
            url: non_empty(&self.litert_url)
                 .unwrap_or("http://localhost:8000".into()),
            model: non_empty(&self.litert_model)
                 .unwrap_or_else(|| model_id.to_string()),
        },
        "ollama" => RuntimeBackend::Ollama {
            url: non_empty(&self.ollama_url)
                 .unwrap_or("http://localhost:11434".into()),
            model: model_id.to_string(),
        },
        "stub" => RuntimeBackend::Stub,
        _ => {                              // auto-detect
            if let Some(url) = non_empty(&self.litert_url) {
                RuntimeBackend::LiteRT {
                    url,
                    model: non_empty(&self.litert_model)
                           .unwrap_or_else(|| model_id.to_string()),
                }
            } else if let Some(url) = non_empty(&self.ollama_url) {
                RuntimeBackend::Ollama { url, model: model_id.to_string() }
            } else {
                RuntimeBackend::Stub
            }
        }
    }
}
🧪 Tests it must pass
  • test_auto_detect_stub_when_empty — nothing set ⇒ stub
  • test_auto_detect_ollama — only OLLAMA_URL ⇒ ollama, model = model_id
  • test_auto_detect_litert — only LITERT_URL ⇒ litert
  • test_litert_preferred_over_ollama — both URLs set ⇒ litert
  • test_explicit_backend_overrides — both URLs set, backend=ollama ⇒ ollama
  • test_explicit_stub — ollama URL set, backend=stub ⇒ stub
  • test_litert_model_override — LITERT_MODEL beats model_id

SHA-256 artifact verification
medium
Given downloaded bytes and an expected hex SHA-256, return Ok(()) on match and a descriptive error on mismatch. This is the gate that stops tampered weights from loading.
💡 Hints
  • Use the sha2 crate: Sha256::new(), update(bytes), finalize().
  • hex::encode(...) the digest, then compare strings.
  • On mismatch, include both expected and actual in the error — invaluable in logs.
✅ Reference solution (Rust) 
pub fn verify_artifact(model_id: &str, bytes: &[u8],
                       expected_sha256: &str) -> Result<()> {
    let mut hasher = Sha256::new();
    hasher.update(bytes);
    let actual = hex::encode(hasher.finalize());

    if actual != expected_sha256 {
        bail!("artifact SHA-256 mismatch: expected {expected_sha256}, got {actual}");
    }
    Ok(())
}
🧪 Tests to write
  • verify_ok — bytes whose real digest equals expected ⇒ Ok
  • verify_mismatch — wrong expected hash ⇒ Err, message contains both hashes
  • verify_empty — empty slice hashes to the known SHA-256 of "" (e3b0c442...)
Why it matters: content addressing means the hash is the identity of the artifact. Verify-before-load is the whole integrity story — there is no second chance once weights are in memory.

Device-deployment state transition
harder
Model the per-device lifecycle pending → downloading → verifying → running, where any state can jump to failed. Implement next(state, event) and reject illegal transitions.
FromEventTo
PendingStartDownloadDownloading
DownloadingDownloadDoneVerifying
VerifyingVerifyOkRunning
anyError(msg)Failed(msg)
Running / Failedanything else(illegal — terminal)
💡 Hints
  • Model states and events as enums; match (state, event) on the pair.
  • Error is a wildcard arm that applies in any non-terminal state.
  • Return Result<State, IllegalTransition> so callers can't silently skip a step.
✅ Reference solution (Rust) 
#[derive(Debug, Clone, PartialEq)]
enum State { Pending, Downloading, Verifying, Running, Failed(String) }

enum Event { StartDownload, DownloadDone, VerifyOk, Error(String) }

fn next(state: State, ev: Event) -> Result<State, String> {
    use State::*; use Event::*;
    match (state, ev) {
        (_, Error(m))                  => Ok(Failed(m)),
        (Pending,     StartDownload)   => Ok(Downloading),
        (Downloading, DownloadDone)    => Ok(Verifying),
        (Verifying,   VerifyOk)        => Ok(Running),
        (s, _) => Err(format!("illegal transition from {s:?}")),
    }
}
🧪 Tests to write
  • happy_path — Pending→Downloading→Verifying→Running
  • error_from_any — Error from Downloading ⇒ Failed("...")
  • illegal_skip — VerifyOk while Pending ⇒ Err
  • terminal_running — any event on Running (except… none) ⇒ Err
Note the ordering: the Error arm comes first so it wins from any state. Put it last and the wildcard (s, _) would swallow it.

Design drill — "Add a rollback"

Prompt: A deployment to location=barcelona ships a bad model — devices reach running but telemetry shows TTFT spiking and errors climbing. Design a one-click rollback to the previous model for the affected devices. You have 15 minutes — sketch the API, data, and agent changes.

🧭 Discussion framework
  • What "previous" means: you need history. Each device has a current_model_id; persist the prior deployment per device (or keep an ordered deployment log) so rollback has a target.
  • API surface: POST /api/deployments/{id}/rollback creates a new deployment pointing at the previous artifact_url + SHA for the same tag selector. Rollback is just a forward deploy of an older artifact — reuse the whole pipeline.
  • Integrity still applies: the old artifact's SHA-256 must still verify; never special-case the security gate for rollbacks.
  • Signal to trigger it: who decides? Manual (operator sees the dashboard) vs. automatic (a watchdog on ClickHouse telemetry: TTFT/error-rate threshold). Start manual; automation is a follow-up.
  • State & events: reuse the existing per-device state machine; emit a rollback event on NATS so the UI and any subscribers update.
  • Failure modes: what if the old artifact is gone? What if only some devices rolled back? Partial-rollback status needs to be visible — lean on the existing per-device deployment status rollup.

Strong answer signal: recognizing rollback is not a new mechanism — it's the existing tag-based deploy aimed at a remembered artifact, with the same SHA gate and the same state machine. The only genuinely new thing is remembering the previous artifact.

Flashcards

Click a card to flip. (When printed, both sides show.)

Q · precedenceWhen RUNTIME_BACKEND is empty, what order does the agent auto-detect backends?
ALiteRT > Ollama > Stub — based on which *_URL env var is set. Stub is the always-available fallback.
Q · integrityWhat does the agent do after downloading an artifact, before loading it?
AComputes SHA-256 over the bytes and compares to the deployment's artifact_sha256. On mismatch it bails and never loads — tampered weights are rejected.
Q · lifecycleName the four per-device deployment states in order (plus the escape hatch).
Apending → downloading → verifying → running, with any state able to fall to failed (carrying an error_msg).
Q · transportHow do devices authenticate to the control plane, and over what?
AgRPC on :9090 over mTLS (TLS 1.3, mutual certs). The agent loads ca.crt / device.crt / device.key from CERT_DIR.
Q · livenessHow and when is a device marked offline?
AA heartbeat watchdog flips it to offline after 30 s of silence. Device status (online/offline) is separate from deployment progress.
Q · storageWhy ClickHouse and Postgres in the same system?
APostgres = low-volume mutable state (devices, deployments). ClickHouse = high-volume append-only telemetry (tps, ttft, mem). NATS carries events between services.
