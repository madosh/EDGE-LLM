Arm SME2 + KleidiAI + LiteRT: a full-stack walkthrough of on-device generative AI on Arm CPUs

An in-depth look at the ISA-level features, micro-kernel library, runtime dispatch logic, and quantization recipe that together deliver >2× inference speedup for diffusion-based generative audio models on commodity Armv9-A CPUs — without an NPU or GPU.

Target ISA: Armv9-A · FEAT_SME2 · FEAT_I8MM · FEAT_BF16 Runtime: LiteRT (TFLite) · XNNPACK · KleidiAI Reference model: stable-audio-open-small (DiT, ~1.1B)

01 Abstract

Generative AI workloads are bandwidth-bound and matmul-bound. Two converging advances — Arm's Scalable Matrix Extension 2 (SME2) on Armv9-A and Google's tightly integrated LiteRT / XNNPACK / KleidiAI stack — eliminate the historical CPU/accelerator tradeoff by giving general-purpose CPUs a first-class matmul datapath with transparent runtime dispatch. This document dissects the layers: from the streaming-mode ZA tile architecture in SME2, through KleidiAI's micro-kernel selection, XNNPACK's graph fusion, up to the LiteRT CompiledModel API and the AI Edge Quantizer's INT8 recipe.

02 Arm SME2: the instruction-set architecture

SME2 is a streaming-mode extension to AArch64 introduced in Armv9.2-A. It is not "just wider SIMD" — it adds an entirely new architectural register file and execution mode dedicated to outer-product matrix accumulation.

The ZA tile and streaming mode

SME defines a 2D architectural register called ZA, an SVL × SVL byte tile where SVL (Streaming Vector Length) is implementation-defined from 128 to 2048 bits per row. ZA is accessed as horizontal or vertical sub-tiles whose element width (8/16/32/64-bit) determines how many tiles can be active simultaneously (16 tiles for INT8/FP16, 4 for FP32, 2 for FP64).

Entry into streaming mode (SMSTART) switches the core's SIMD/FP datapath: Z/P registers become SVL-wide rather than 128-bit NEON-wide, and the dedicated SME matmul unit is gated on. SMSTOP restores normal mode. This separation is what lets vendors implement SME as a shared cluster-level accelerator without committing to a wide-SIMD core.

Key SME2 instructions used by AI kernels

MnemonicOperationUse in inference
FMOPA / BFMOPA FP16/BF16 outer-product accumulate into a ZA tile Core of FP16 GeMM kernels (attention, MLP up/down projections)
SMOPA / UMOPA Signed/unsigned INT8 outer-product into INT32 accumulator INT8 weight × INT8 activation matmul (DiT linear layers)
BMOPA (SME2) Multi-vector bilinear matmul; 2- and 4-way variants Block-quantized GeMM, K-blocking inside iGeMM
LD1W / ST1W + ZA slice Strided load/store of an entire ZA row or column Streaming weights through tiles without spilling to memory
PSEL + predicate regs Per-element masking inside streaming SVE Tail handling, no scalar fallback loop needed
Why this matters Each FMOPA performs an SVL/16 × SVL/16 half-precision outer product in one instruction. On a 512-bit SVL implementation that's a 32×32 FP16 accumulate per cycle — roughly an order of magnitude more arithmetic per dispatch than NEON's FMLA.

Why it's a "cluster-level" accelerator

The SME unit is physically shared across the CPU cluster on most current implementations. Only one core can be in streaming mode at a time per cluster, so KleidiAI's threading model intentionally pins matmul-heavy work to a single SME-eligible core and runs lightweight ops (elementwise, normalisation) on the other cores in parallel.

03 KleidiAI: hand-written micro-kernels

KleidiAI is an Apache-2.0 C library of micro-kernels that wrap the SME2 / I8MM / DotProd ISAs in stable C entry points. It is not an inference engine — it has no graph, no scheduler, no memory planner. It exposes a kernel registry and packing helpers, and lets a host engine (XNNPACK, ggml, ONNX Runtime) choose and call them.

Kernel taxonomy

FamilyVariantsTrigger
GeMM (dense matmul) FP32, FP16, BF16, INT8×INT8→INT32, INT4×INT8 Fully-connected layers, attention QKV/output projections
iGeMM (indirect GeMM) Same dtypes; takes a pointer table instead of a packed tensor Convolutions lowered to im2col, sliding-window ops
Packing lhs_pack, rhs_pack, bias_pack Run once at load time; rearranges weights for the kernel's tile layout
RoPE / LayerNorm / softmax Mostly NEON+SVE; SME2 used only when matmul-shaped LLM and transformer plumbing around the matmul cores

A KleidiAI call site, conceptually

// Pick a micro-kernel based on detected CPU features and operand shapes.
const kai_matmul_ukernel *ukernel = kai_select_matmul_ukernel(
    .has_sme2 = 1,
    .has_i8mm = 1,
    .lhs_dtype = KAI_DT_QSI8,    // dynamic INT8 activations
    .rhs_dtype = KAI_DT_QSI8,    // per-channel INT8 weights
    .dst_dtype = KAI_DT_F32,
    .m = M, .n = N, .k = K);

// One-time weight rearrangement into the kernel's tile-friendly layout.
ukernel->rhs_pack(N, K, weights_q8, scales, packed_rhs);

// Hot path: called every forward pass.
ukernel->run(M, N, K, lhs_q8, packed_rhs, bias, dst_f32,
    /* dst_stride */ N * sizeof(float),
    /* lhs_scale */ act_scale,
    /* activation clamp */ -FLT_MAX, FLT_MAX);
Design lever KleidiAI's "no graph, no allocator" philosophy is deliberate: every kernel is shape-specialized and pre-packed. The host engine pays the packing cost once at model load, then every inference call is a pure compute loop over already-tiled data. This is what makes the SME2 datapath actually saturate.

04 XNNPACK: graph fusion & kernel dispatch

XNNPACK is the high-performance NN operator library that LiteRT delegates CPU operators to. From LiteRT's perspective it is a "delegate" — a plugin that claims a partition of the TFLite graph and replaces it with an opaque compiled subgraph.

Delegate lifecycle

  1. Partition. XNNPACK walks the TFLite graph and marks every node it supports (matmul, conv, FC, transpose-conv, softmax, gelu, layernorm…). Unsupported nodes stay on the TFLite reference interpreter.
  2. Fuse. Inside its partitions XNNPACK rewrites canonical patterns: Conv → BiasAdd → ReLU becomes a single fused op; MatMul → Add → Gelu becomes a fused FC; Quantize → MatMul → Dequantize collapses to a dynamic-quant matmul (the key pattern for INT8 inference).
  3. Plan. Tensor lifetimes are analysed and a single scratch arena is allocated. Weights are packed once via KleidiAI's rhs_pack.
  4. Dispatch. On every Invoke() XNNPACK selects per-op micro-kernels based on runtime CPU features. The selection table is queried once at CompiledModel::Create time and cached.

Dispatch priority (FP16/BF16 matmul, AArch64)

Tier 1
SME2 FMOPA (KleidiAI kai_matmul_clamp_f16_f16_f16p_sme)
Requires FEAT_SME2. Picked when M ≥ 8.
Tier 2
NEON+FP16 + dotprod (KleidiAI …_neon_dotprod)
Requires FEAT_FP16, FEAT_DotProd. Used on Armv8.2 → 8.6.
Tier 3
Pure NEON FMLA (XNNPACK native)
Baseline Armv8-A.
Fallback

Should never trigger on any production phone; correctness only.
Small-M caveat For autoregressive decode steps (M=1), SME2's outer-product geometry is wasted. KleidiAI exposes a dedicated gemv family that uses streaming SVE without entering ZA mode — XNNPACK switches to it automatically when the batch dimension is 1.

05 LiteRT: runtime & the CompiledModel API

LiteRT is the rebranded TensorFlow Lite runtime, hardened and re-exposed via a modern C++ API (litert::CompiledModel) that abstracts hardware delegate selection behind a single enum.

// 1. Initialize the LiteRT environment (singleton, holds delegate registry).
auto env = litert::Environment::Create({}).value();

// 2. Compile a .tflite for a target accelerator family.
//    HwAccelerators::kCpu transparently selects XNNPACK + KleidiAI.
auto compiled = litert::CompiledModel::Create(
    env, "dit_int8.tflite", litert::HwAccelerators::kCpu).value();

// 3. Allocate I/O buffers (zero-copy where the delegate permits).
auto inputs  = compiled.CreateInputBuffers().value();
auto outputs = compiled.CreateOutputBuffers().value();

// 4. Map and fill an input tensor in-place.
{
  auto lock = scoped_lock<float>(inputs[0],
                                  TensorBuffer::LockMode::kWrite);
  std::memcpy(lock.data(), conditioning, conditioning_bytes);
}

// 5. Run. Blocking, single-call; threading handled by XNNPACK internally.
compiled.Run(inputs, outputs);

// 6. Read back the generated waveform (float32 PCM).
{
  auto lock = scoped_lock<const float>(outputs[0],
                                        TensorBuffer::LockMode::kRead);
  write_wav("out.wav", lock.data(), lock.size());
}

06 Quantization recipe (AI Edge Quantizer)

The AI Edge Quantizer is a graph-rewriting tool that consumes a recipe describing which nodes to quantize, how, and to what precision. The DiT submodule of stable-audio-open-small uses dynamic per-channel INT8 weight quantization with FP32 activations — sometimes called "INT8 dynamic" or W8A_fp.

The recipe

from ai_edge_quantizer import quantizer

recipe = [{
    'regex'         : '.*',                          # match every op
    'operation'     : '*',
    'algorithm_key' : 'min_max_uniform_quantize',
    'op_config': {
        'weight_tensor_config': {
            'num_bits'    : 8,
            'symmetric'   : True,                    # zero_point = 0
            'granularity' : 'CHANNELWISE',            # one scale per output channel
            'dtype'       : 'INT',
            'block_size'  : 0,                       # 0 = no sub-channel blocking
        },
        'compute_precision'  : 'INTEGER',            # INT8 × INT8 → INT32
        'explicit_dequantize': False,                # keep the fused W8A_fp pattern
        'skip_checks'        : False,
        'min_weight_elements': 0,
    },
}]

qt = quantizer.Quantizer('dit_fp32.tflite', recipe)
qt.quantize().export_model('dit_int8.tflite', overwrite=True)

What the algorithm actually does

For each weight tensor W ∈ ℝ(Cout, Cin) and each output channel c:

  1. Compute scale[c] = max(|W[c, :]|) / 127. Symmetric, so no zero-point.
  2. Store W_int[c, k] = round(W[c, k] / scale[c]) clipped to [-127, 127].
  3. At inference, activations are quantized dynamically: per-token per-tensor symmetric scale computed at runtime, then INT8 matmul, then dequantize the INT32 accumulator using act_scale × weight_scale[c].
Why this scheme wins for DiT The diffusion transformer is almost entirely dense linear projections (~90 % of its FLOPs). Weights are stable and well-distributed → per-channel symmetric INT8 captures them with <1 % MSE. Activations are highly variable (attention scores, time embeddings) → keeping them in FP32 / FP16 avoids the calibration headache of static activation quant. The result is INT8 throughput on the hot path with FP precision wherever it matters.

Validating with Model Explorer

Model Explorer's node-data overlay plugin renders a per-op error metric (median difference ratio between the FP32 and quantized run) as a color overlay on the graph. A green block ⇒ < 2 % MSE, safe to leave INT8. A red block ⇒ keep this op FP16/FP32. The blog's screenshot shows every DiT transformer block green, which is what justified blanket-quantizing the submodule with a single regex: '.*' rule.

Single-shot conversion + quantization

import ai_edge_torch
from ai_edge_torch.quantize import quant_config
from ai_edge_torch.generative.quantize import quant_recipe, quant_recipe_utils

qcfg = quant_config.QuantConfig(
    generative_recipe=quant_recipe.GenerativeQuantRecipe(
        default=quant_recipe_utils.create_layer_quant_dynamic(),
    )
)

edge = ai_edge_torch.convert(model, example_inputs, quant_config=qcfg)
edge.export('dit_int8.tflite')
Conversion gotcha ai_edge_torch.convert requires example_inputs with the exact shapes you intend to deploy. Dynamic shape support is partial; if the DiT runs with variable sequence length, export multiple SignatureDefs or pad to a fixed bucket.

08 Case study: the DiT submodule

stable-audio-open-small is a latent diffusion model with three submodules: a T5-style text encoder (kept FP16), a Diffusion Transformer (DiT, quantized to INT8), and a VAE-like autoencoder decoder (kept FP16 because its conv layers are quantization-sensitive). The DiT dominates wall-clock time: each generation step runs it once, and the schedule does ~100 steps per 11-second clip.

Operator breakdown (DiT, per step)

Op family% of step time (FP32)Quant target% of step time (INT8)
Linear projections (QKV, MLP)72 %INT8 W8A_fp31 %
Attention scores + softmax14 %FP1619 %
LayerNorm / GroupNorm5 %FP167 %
Time / class embeddings3 %FP164 %
Memory / packing overhead6 %—9 %
Wall clock per step100 %—~33 %

Net: a ~3× speedup on the DiT submodule alone, which propagates to a ~2.1× end-to-end speedup once the unquantized autoencoder, text encoder, and waveform post-processing are amortised back in.

10 Runtime capability detection

A fleet manager (or any deploy-time scheduler) needs to know which CPU features a target device exposes before assigning it a model variant. Below are the canonical detection paths.

Linux / Android (/proc/cpuinfo + HWCAPs)

use std::fs;

pub fn detect_arm_features() -> Vec<(&'static str, String)> {
    let cpuinfo = fs::read_to_string("/proc/cpuinfo").unwrap_or_default();
    let flags  = cpuinfo
        .lines()
        .find(|l| l.starts_with("Features"))
        .map(|l| l.to_string())
        .unwrap_or_default();

    let has = |f: &str| flags.split_whitespace().any(|x| x == f);

    vec![
        ("cpu.arch",           std::env::consts::ARCH.to_string()),
        ("cpu.isa.neon",      has("asimd").to_string()),
        ("cpu.isa.dotprod",   has("asimddp").to_string()),
        ("cpu.isa.i8mm",      has("i8mm").to_string()),
        ("cpu.isa.bf16",      has("bf16").to_string()),
        ("cpu.isa.sve",       has("sve").to_string()),
        ("cpu.isa.sve2",      has("sve2").to_string()),
        ("cpu.isa.sme",       has("sme").to_string()),
        ("cpu.isa.sme2",      has("sme2").to_string()),
    ]
}

macOS / Apple Silicon (sysctl)

$ sysctl -a | grep -E 'hw.optional.(arm.FEAT_|AdvSIMD|neon)'
hw.optional.arm.FEAT_DotProd: 1
hw.optional.arm.FEAT_I8MM:    1
hw.optional.arm.FEAT_BF16:    1
hw.optional.arm.FEAT_SME:     1

hw.optional.AdvSIMD:          1
Don't trust the kernel alone Some early SME2-capable cores expose the feature flag but ship with a microcode-disabled SME unit. Always run a 1×1 KleidiAI warmup matmul at agent startup and time it — if it doesn't beat the NEON path, downgrade the reported cpu.isa.sme2 label to false.

11 Integrating into Cami Fleet

Concrete changes that turn this paper into shipped code in the existing cami-fleet/ repo.

Agent (Rust)

  1. agent/src/capability.rs (new). Implement the detector from §10, plus a startup warmup matmul. Cache results in OnceCell<HwLabels>.
  2. agent/src/config.rs. Merge HwLabels into the existing DEVICE_LABELS map before RegisterRequest is sent.
  3. agent/src/model_runtime.rs. Extend Telemetry with accel: String ("xnnpack-kleidiai-sme2" / "xnnpack-kleidiai-neon" / "stub") and parse it from LiteRT's /v1beta/diagnostics endpoint when available.

Control plane (Go)

  1. control-plane/proto/device.proto. Add map<string,string> capabilities = N; to RegisterRequest. The existing label selector already handles arbitrary keys, so deployments can target cpu.isa.sme2=true with zero schema changes downstream.
  2. store/postgres/. Add columns artifact_format (litert | gguf | safetensors), weight_precision (fp32 | fp16 | int8 | mixed-fp16-int8), quantizer.
  3. api/rest/. Surface those fields on POST /api/deployments and GET /api/devices/:id.

Dashboard (SvelteKit)

  1. Fleet-overview chart: stacked bar of devices grouped by cpu.isa.sme2 / sve2 / neon-only.
  2. Device-detail card: a HardwareCapabilities component listing every cpu.isa.* label as colored chips.
  3. Deploy form: precision dropdown (fp32 / fp16 / int8 / mixed) wired to a "compatible devices: N" preview that re-queries on selector change.
Why this is a small change Cami Fleet's deployment model is already label-driven (tag_selector: {"location": "barcelona"}). Adding hardware-capability labels reuses the existing matcher entirely — no new selector logic, no new gRPC RPCs, just richer metadata on the devices and on the deployments.
