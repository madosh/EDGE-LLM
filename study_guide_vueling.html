Spotlight — Edge LLM · Cami Fleet

Cami Fleet answers one question: how do you safely push an AI model to a fleet of edge devices you don't physically control, and prove it actually ran? The system is split into three cooperating programs, each in the language that fits its job.

Control plane Go 1.23

The brain. Exposes a REST API (:8080) for operators and a gRPC server (:9090, mTLS) for devices. Tracks device state and deployments in Postgres, telemetry in ClickHouse, and fans out events over NATS.

Device agent Rust

Runs on each edge device. Registers, heartbeats, watches for deploy instructions, then downloads → verifies → loads → reports. Talks to a pluggable inference runtime (LiteRT, Ollama, or a stub).

Operator UI SvelteKit

The dashboard. Fleet overview, a deploy form (model + SHA + tag selector), and per-device detail with live telemetry charts.

Why it matters

Edge AI means weak trust and weak networks. Cami Fleet leans on content-addressed artifacts and mutual TLS so a device can refuse tampered weights and the control plane only talks to devices it issued certs to.

The 30-second pitch

"Cami Fleet is a fleet manager for edge AI. An operator picks a model and a tag selector like location=barcelona; the control plane records a deployment and the matching Rust agents pull the artifact, verify its SHA-256, load it into their runtime, and stream tokens/sec and latency back. Devices authenticate with mutual TLS over gRPC, and a 30-second heartbeat watchdog flips silent devices to offline. Three stores: Postgres for state, ClickHouse for time-series telemetry, NATS for events."

Architecture at a glance

Three planes: operator → control plane → edge. The operator browser only ever speaks REST. Devices only ever speak gRPC (mTLS). The control plane is the only thing that touches the data stores.

Operator Browser
   │  REST /api  (X-Api-Key)
   ▼
Control Plane (Go)          ┌── Postgres 16   device state + deployments
   ├ REST   :8080  ─────────┼── ClickHouse    inference telemetry
   └ gRPC   :9090  (mTLS)   └── NATS          event bus
   ▲
   │  gRPC + mTLS (TLS 1.3, mutual certs)
   ▼
Edge Devices (Rust agents)  ┄┄►  LiteRT / Ollama / Stub  (inference)
Why two protocols? REST is friendly for humans and the browser; gRPC gives the agent a typed, streaming, mutually-authenticated channel that's cheap to keep open for heartbeats and telemetry.

End-to-end: from "deploy" to "running"

1 · Operator POSTs deployment→ 2 · Control plane matches tag selector→ 3 · Agents see instruction on heartbeat→ 4 · download→ 5 · verify SHA-256→ 6 · load into runtime→ 7 · stream telemetry 
SHA=$(cat artifacts/sample-gemma-4-e2b.tar.gz.sha256)

curl -s -X POST http://localhost:8080/api/deployments \
  -H "X-Api-Key: changeme" \
  -H "Content-Type: application/json" \
  -d '{
    "model_id": "gemma-4-e2b",
    "artifact_url": "http://control-plane:8080/artifacts/sample-gemma-4-e2b.tar.gz",
    "artifact_sha256": "'"$SHA"'",
    "tag_selector": {"location": "barcelona"}
  }'

Each matching device then cycles pending downloading verifying running within seconds.

Concept · Tag-based deployment

You never deploy to a device by ID. You deploy to a label selector, and the control plane resolves which devices match. Labels are arbitrary key=value pairs set on each agent (e.g. location=barcelona,type=jetson-orin).

Agent side

Labels come from DEVICE_LABELS and are parsed into a map. Empty pairs are skipped; whitespace is trimmed.

Control-plane side

A deployment carries a tag_selector map. A device matches when it satisfies every key in the selector.

Mental model: it's Kubernetes label selectors for a fleet of AI devices. Decoupling intent ("barcelona devices") from identity ("device-7c3f") is what makes it scale to N devices.

Concept · The two state machines

Deployment status (control plane's view)

pending→ in_progress→ completed /failed

Per-device deployment status (agent's view)

pending→ downloading→ verifying→ running / any →failed
StateWhat just happened
pendingDevice matched the selector; instruction queued, not yet started.
downloadingAgent is pulling the artifact from artifact_url.
verifyingComputing SHA-256 of the bytes and comparing to artifact_sha256.
runningModel loaded into the runtime; telemetry streaming.
failedDownload error, SHA mismatch, or load failure — carries an error_msg.
Easy to confuse: there are two status enums. Deployment status (pending/in_progress/completed/failed) is the rollup the operator sees; device-deployment status (pending/downloading/verifying/running/failed) is per device. A deployment is completed only when its devices finish.

Concept · Security & integrity

Content-addressed artifacts

Every deployment includes the expected artifact_sha256. The agent hashes the downloaded bytes and refuses to load on mismatch — tampered or corrupted weights never reach the runtime.

Mutual TLS (mTLS)

Device ↔ control-plane gRPC runs over TLS 1.3 with mutual certificates. The agent loads ca.crt, device.crt, device.key from CERT_DIR. Both sides prove identity.

One-liner: mTLS answers "is this device allowed to talk to me?"; SHA-256 answers "are these the exact bytes I published?" Two different trust questions, two mechanisms.

Concept · Pluggable inference backends

The agent abstracts the runtime behind a RuntimeBackend enum with three variants. Selection is explicit via RUNTIME_BACKEND, or auto-detected.

BackendTriggerBest for
LiteRTLITERT_URL setEdge devices with NPU/GPU (Pixel, MediaTek, Qualcomm)
OllamaOLLAMA_URL setx86/ARM servers, CUDA or CPU
Stubdefault / fallbackCI, demos, dev without a runtime
Auto-detect precedence: if no explicit backend, the agent prefers LiteRT > Ollama > Stub based on which URL env var is set. An explicit RUNTIME_BACKEND always overrides auto-detection.
Gotcha worth knowing: Google LiteRT is genuinely an on-device runtime. In the control-plane agent, the "LiteRT" backend is actually an HTTP client to a Gemini-compatible :generateContent endpoint. For the real on-device runtime loading a model on a phone, see examples/litert-android.

Concept · Telemetry & offline detection

Once running, the agent streams metrics that land in ClickHouse:

MetricMeaning
tpsTokens per second — throughput
ttft_msTime to first token — responsiveness
mem_mbResident memory of the loaded model
Offline detection: a heartbeat watchdog flips a device to offline after 30 s of silence. Device status is a simple online/offline enum, separate from deployment progress.

Q&A drills

Why three different languages?

Each layer plays to a language's strength: Go for a concurrent network service (REST+gRPC, easy goroutines), Rust for a small, safe, long-running agent on constrained devices (no GC pauses, memory safety), and SvelteKit for a reactive operator UI. The contract between them is the proto/REST schema, so they evolve independently.

Walk me through what happens when I deploy a model.

Operator POSTs /api/deployments with model_id, artifact_url, SHA-256, and a tag_selector. The control plane persists the deployment and computes matching devices from their labels. On their next gRPC heartbeat, matching agents receive the instruction and move pending→downloading→verifying→running: pull the artifact, hash it and compare to the expected SHA, load it into the resolved backend, then stream tps/ttft/mem telemetry. Failures at any step set the device-deployment to failed with an error message.

How does a device refuse a tampered model?

The deployment ships the expected artifact_sha256. After download, the agent computes SHA-256 over the bytes; if it doesn't match, it bails with a "SHA-256 mismatch" error and never loads the weights. Content addressing means the hash is the integrity guarantee.

What's the difference between deployment status and device status?

Three separate enums. Device status: online/offline (liveness). Deployment status: pending/in_progress/completed/failed (the operator's rollup). Device-deployment status: pending/downloading/verifying/running/failed (one device's progress on one deployment). Mixing these up is the classic onboarding trip-up.

Which inference backend runs, and who decides?

The agent's config resolves it. If RUNTIME_BACKEND is set (litert/ollama/stub) that wins. Otherwise it auto-detects with precedence LiteRT > Ollama > Stub by checking which *_URL is set, defaulting to Stub so CI and demos always work with no runtime.

Why ClickHouse and Postgres?

Different shapes of data. Postgres holds low-volume, mutable state (devices, deployments) where transactions and joins matter. ClickHouse holds high-volume, append-only time-series telemetry where columnar scans and aggregation over millions of points are the workload. NATS carries the ephemeral events between services.
